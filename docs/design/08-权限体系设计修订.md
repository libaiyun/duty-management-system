# 权限体系设计修订

本文记录人员类型、业务资格、账号权限、RBAC、机房业务边界、个人业务操作和月份锁定的最新设计结论。后续相关设计、开发和验收以本文为准。

### 一、人员类型与业务资格

人员类型只保留四种：

- 值机员
- 检修班
- 机房主任
- 机房副主任

人员类型只决定业务资格，不授予任何功能权限。

具体规则：

- 只有值机员可以参与周期排班。
- 值机员可通过“参与排班”字段决定是否进入排班候选范围。
- 非值机员不能设置为参与排班。
- 值机员之间的班次替换统一称为“换班”：
  - 单向替班
  - 双向换班
- “顶班”仅发生在值机员请假获批后。
- 顶班人只能是检修班、机房主任或机房副主任。
- 值机员不能作为请假流程中的顶班人。

### 二、账号、角色和功能权限

取消当前固定角色矩阵，不再通过“值机员、主任”等角色决定权限。

采用“RBAC + 账号直接权限”：

```text
账号有效权限 = 所属角色权限并集 + 账号直接授予权限
```

第一版不设计拒绝权限或权限减法。

账号管理支持：

- 创建、编辑、启停账号
- 绑定人员
- 分配角色
- 直接分配功能权限
- 查看最终有效权限
- 查看权限来源

角色管理支持：

- 创建、编辑、停用角色
- 按功能分组分配权限
- 查看关联账号
- 初始化若干常用角色

角色按照工作职责设计，不与人员类型绑定，例如排班管理员、审批管理员、人员资料管理员、财务统计等。

### 三、权限点

系统拆分明确的功能权限点，并按模块分组，例如：

- 排班管理
- 换班审批
- 请假审批与顶班安排
- 人员管理
- 班次和排班规则
- 节假日与费用标准
- 退费管理
- 考勤管理
- 账号和角色管理
- 组织机构
- 日志、备份等系统管理

权限点由系统代码和数据库迁移统一注册，用户只能分配，不能随意创建权限编码。

同一权限点可以同时控制：

- 页面和菜单
- 页面操作按钮
- 后端 API

无权限菜单直接隐藏；直接访问无权限页面时原则上进入 403，后端 API 必须独立进行权限校验。

### 四、个人业务操作

以下本人操作不受功能权限影响：

- 查看本人相关排班、换班、请假和顶班
- 发起、撤回本人换班
- 发起、撤回本人请假
- 确认、拒绝发给本人的换班
- 确认、拒绝安排给本人的顶班
- 查看本人考勤、退费等个人结果

这些操作仍须经过业务校验：

- 是否为业务相关人员本人
- 是否属于对应机房
- 是否绑定有效人员和账号
- 是否符合换班或顶班资格
- 排班是否已经发布
- 是否为历史日期
- 当前流程状态是否允许操作
- 是否存在重复申请或并发冲突

个人页面不依赖功能权限，可根据账号是否绑定人员及人员业务资格决定是否展示入口。

### 五、超级管理员和系统管理员

超级管理员：

- 采用账号级特殊标记识别。
- 不依赖角色或权限记录。
- 不受任何功能权限影响。
- 权限检查直接放行。
- 仍应遵守业务状态和数据完整性规则。
- 普通管理员不能删除、停用或修改其超级管理员身份。

系统管理员：

- 作为内置角色初始化。
- 初始化时授予当时存在的全部功能权限。
- 后续新增权限不会自动获得。
- 初始化后允许调整其权限。
- 仍受正常权限校验、账号状态和业务规则约束。
- 内置角色可以禁止删除，但允许调整权限。

### 六、机房边界

系统不再提供可配置的数据权限，也不再使用角色数据范围。

普通账号的业务数据范围固定为绑定人员所属机房：

- 具有“人员管理”权限的普通账号，只能管理所属机房人员。
- 其他机房业务功能同样只能操作所属机房数据。
- 这是固定业务边界，不是可配置数据权限。

系统管理员和超级管理员在机房业务页面通过顶部机房切换器选择当前机房。

账号、角色、组织机构、日志、备份等全局页面不依赖当前机房，但仍受对应功能权限控制。

可以删除 `sys_data_scope`，但必须保留后端的人员归属、当前机房和跨机房操作校验。

### 七、取消月份锁定

取消跨模块的“月份锁定”设计，包括：

- 排班 `locked` 状态
- `locked_at`
- 锁定月份接口和按钮
- 锁定月份权限点
- “已锁定月份禁止业务操作”的统一判断
- 月份归档对所有业务操作的一刀切冻结

普通流程改为按班次日期限制：

- 历史班次不能发起换班或请假。
- 不能确认已经进入历史日期的换班或顶班。
- 历史班次不能执行普通排班调整。
- 历史数据需要修改时，使用独立的“历史修正”功能。
- 历史修正必须填写原因并写入变更台账。

退费批次和考勤批次自身的确认或锁定属于报表生命周期，不再反向冻结排班、换班、请假和顶班。历史修正导致结果变化时，应将已有考勤或退费结果标记为需要重新生成。

### 八、重构和迁移策略

本次重构不考虑历史数据迁移：

- 现有历史数据可以清空。
- 直接建立最终数据模型。
- 删除旧固定角色矩阵和数据范围结构。
- 清理代码中对固定角色编码的判断。
- 将现有 Alembic 迁移合并为一个新的 baseline。
- baseline 一次性创建最终表结构、权限点、内置角色和内置账号。
- 不编写旧权限、旧角色和旧状态的转换脚本。
